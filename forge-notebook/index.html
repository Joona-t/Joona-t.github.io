The Forge Notebook

Two days of putting a local language model on one home PC with two graphics cards: what we installed, what we measured, what broke, and how we found it. Every number here comes from a log on the machine. Where something is a guess, it says so.

The Forge is a desktop with an RTX 3090 Ti and an RTX 3090 (48 GB of graphics memory between them), a Ryzen 9 9950X and 64 GB of DDR5. The model is Qwen3.8-27B. Several Claude Code sessions worked on it at once; this notebook follows all of them.

Why FP8. The model was only on disk in Ollama's format, which vLLM can't read. Two builds fit the two cards: a 4-bit one (19.5 GB) and Qwen's own FP8 build (30.9 GB). The owner picked FP8: Use FP8 instead. It is the closest to the 8-bit build the agent had been using on Ollama. It is still a different quantization, so results from the two are never compared as if they were the same model.

Why two modes. vLLM wants both cards for itself and serves many requests at once. The existing agent and its evals were built on Ollama, one job at a time. A single lock file decides which one owns the cards (see The GPU lock).

What was chosen, and why

FP8 cache, text-only and MTP: the fastest at every load level, with 254,000 tokens of shared context. Sixteen requests can each hold about 15,800 tokens; four can hold about 63,000 each. One request is capped at 65,536.

Throughput levels off near 165 tokens/s from 8 requests up. What limits it was not profiled. Peak draw was 676 to 693 W for both cards in every setting.

The first quick test at 22:27 (30-token prompts, one run each) showed 47.9, 166.6 and 301.8 tokens/s at 1, 4 and 8 requests. Short prompts make it look much faster; the 2,300-token prompts above are closer to real agent work.

Round 2 (22:51 to 23:02) failed to start both combined settings. That was not the settings: it was the start of the memory fault. The same settings started first time at 23:56.

How jobs share the cards

The two-mode GPU lock

The rules that came out of the night

  1. Ollama mode: every command that makes the model generate runs under the lock, even a single test call.
  2. vLLM mode: never send a request to Ollama. It would try to load 37 GB into memory vLLM is using.
  3. Installs, downloads, builds and unpacking go through forge-heavy: wait for the lock, 4 cores, low priority. Added after the 21:31 hard stop.
  4. Wait on a done-marker in a log file, never on a process-name match.
  5. Before a benchmark or timed eval, wait until the server shows 0 running and 0 waiting requests.

Three engines, three days of the same idea

MTP on and off

Qwen3.8 ships with a small extra head that guesses the next few tokens. The engine checks the guesses in one pass and keeps the ones that match. It was measured three times on the Forge, each time in a different engine.

Cost: MTP made Ollama read long prompts about half as fast (2,971 to 1,626 tokens/s). In vLLM the draft head costs shared context (364,544 to 253,952 tokens).

2026-11-11 22:51 to 2026-11-12 12:57

The memory fault

At 22:51 vLLM stopped starting. Every start crashed while Python was loading modules, at a different place each time. Fresh caches didn't help, and every installed file matched its checksum (108,823 package files). Then a plain CPU-only Python script crashed 2 times in 48 runs, and the kernel logged 5 faults in 7 minutes. That pointed away from vLLM and at the machine.

The test that caught it is forge-memcheck: fill 36 GB of memory with known patterns, read them back 8 or 16 times, and report any byte that comes back wrong.

What every error looked like

One 64-byte line. In 14 of 16 events saved that night, exactly 8 bytes were wrong, every 4th byte, inside a span starting at byte 0x12. Read again a moment later, they were correct. Different addresses each time.

What that shape suggests

Bad memory cells would sit at fixed addresses and stay wrong. A fixed position inside the line, at random addresses, gone on the next read, looks more like one wide 256-bit read going wrong for an instant. That points at the processor's path to memory (memory speed settings, CPU tuning) more than at a faulty stick. [reading, not proven]

A test pinned to each core one at a time compared 3,500 GB and found nothing. Small, one-core loads didn't trigger it; the full 36 GB fill did.

How the reading changed through the night

Heat or load? At 02:05 and 02:07 the check failed right after 18 minutes of both cards working (GPU 1 at 77 °C), and passed at 02:09 once they cooled. It looked like heat.

Not heat. At 03:26 it failed with the cards cool and idle (34 and 42 °C, about 20 W each). At 08:15 it failed after 45 minutes with nothing running, cards at 29 and 39 °C, memory modules at 41 °C.

Something changed at 06:38 and stayed changed. From 05:42 to 06:38, 1 of 11 checks failed. At 06:38 the llama.cpp benchmark stopped vLLM, read about 90 GB of model files and started vLLM again. After that, 12 of 13 failed. One explanation that fits: the errors sit in one region of physical memory, and whether a check lands there depends on what else fills memory. [reading, not proven]

The fix, 12:57, and the advice it went against. The advice at 12:36 was to load BIOS defaults (F5), on the guess that EXPO was on and pushing the memory too hard. That guess was never checked; the running memory speed couldn't be read without sudo. In the BIOS the owner found the memory at the board's default 4800 MT/s with EXPO off, so defaults would have changed nothing about it. They followed an instinct instead: kept the CPU tuning and turned EXPO on, the kit's tested profile (6000 MT/s with its own voltages and timings). I just had a feeling and followed my intuition. It worked.

Worth remembering. This is a plain example that even a capable, intelligent AI can be wrong. The advice came from a model that had read every log of the night, and it still rested on a guess it never checked, delivered as "the most likely fix". What found the fix was a person's instinct about their own machine, and the willingness to go against the advice. Ask what the AI is assuming, check it when it matters, and trust your own read.

Retest, 16 passes per check: clean right after boot, clean twice after filling 55 GB of memory with model files (the pattern that failed 12 of 13 times), clean twice after 16.5 minutes of 16-way vLLM load. The load run held 165 to 167 tokens/s with 0 request errors and GPU 1 at 75 °C.

Two readings are still open: EXPO's settings fixed it, or the fresh boot did (the night before, each boot also started clean and got worse over hours). Hours of real use with checks will tell. If errors come back, the next step is CPU tuning back to defaults.

Heat and power

The bottom card whines. Under load it makes a high-pitched noise. That is almost certainly coil whine: its power coils vibrate when it draws near its limit (366 of 370 W at 80 °C with the fan at 53%). Annoying, not dangerous.

Front fans, 05:36. After the power-off the owner added front fans. GPU 1 now idles at 32 °C instead of 51 to 54 °C, and a spot reading under load showed 63 °C at 360 W against 80 °C before. Under the eval's sustained load it still reaches 76 to 79 °C, so the fans help most at rest. [two different workloads, not a controlled comparison]

The best lesson of the night

One .git trick (writing .git/commondir) first reported an error, then "OK" with nothing changed on disk. A hand run settled it: inside the sandbox the write lands on a placeholder that is thrown away when the command ends. Without the fence, git really does follow it. The route is real and the sandbox closes it. It was missed at first because the stand-in fence used for testing made all of .git read-only: stricter than the real sandbox in exactly the place that mattered.

Known gaps, stated in the report: a repository the agent creates in a sub-folder can hold hooks, and other git state such as an unfinished rebase was not tested.

2026-11-12 04:11 onwards, handoff session

The 20-task eval on vLLM

Twenty small coding tasks, each with its own check script. Two versions of the agent, identical except for 12 lines: side A is main; side B also lets the agent run bash script.sh inside the sandbox. In the Ollama baseline, 27 of 144 tool errors were refused bash calls. One agent at a time, 300 s and 30 turns per task.

The protocol (the owner's: do tests in batches): batches of 5 task runs, a memory check before and after each. A batch counts only if both checks are clean; otherwise it is kept apart as "suspect" and re-run once at the end. The side that goes first alternates.

What it shows so far

Run 1 on side A passed 19 of 20 at a median of 93.5 s per task, the first baseline for the FP8 model on vLLM.

Told plainly, so they don't repeat
